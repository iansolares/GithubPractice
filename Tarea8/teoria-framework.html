Teoría: Frameworks y Bootstrap

Esta página está hecha con Bootstrap, así que en cada bloque primero van a ver el resultado ya renderizado y justo debajo el código que lo genera — igual que en la documentación oficial. Pero antes de entrarle a eso, veamos qué problema resuelve un framework y por qué Bootstrap está armado como está.

1. El problema que resuelve un framework de CSS

Cuando un sitio crece, el CSS escrito a mano se empieza a poner difícil de mantener: cada quien le pone nombre distinto a sus clases, un botón "azul" en una página termina siendo un azul distinto al de otra, y arreglar un estilo en un lugar rompe otra cosa en otro lado. Un framework de CSS existe para eso: pone un mismo set de clases, colores y tamaños que todo el equipo usa igual, para que "botón primario" siempre signifique lo mismo en cualquier parte del sitio.

No todos los frameworks lo resuelven de la misma forma

Hay básicamente tres formas de hacerlo:

  • Basados en componentes (Bootstrap, Bulma, Foundation): te dan piezas ya armadas y con estilo — un navbar, una card — ya listas para usar. Avanzas rápido, pero si no personalizas nada, dos sitios con el mismo framework se ven parecidos entre sí.
  • Utility-first (Tailwind CSS): no te dan componentes armados, te dan muchísimas clases chiquitas que cada una hace una sola cosa (p-4, text-center, flex), y tú armas tu propio componente combinándolas. Tienes más control sobre cómo se ve, pero el HTML termina con muchas más clases por elemento.
  • Sin estilo (headless) (Radix, Headless UI): no traen ni un color — solo resuelven que un dropdown abra bien con el teclado o que un modal funcione como debe, y el diseño completo lo pones tú.

Bootstrap en realidad es una mezcla de las dos primeras: te da componentes armados (navbar, card, carousel) pero TAMBIÉN te da un montón de clases chiquitas de una sola cosa (d-flex, text-center, p-4) — de hecho esas ya las han usado en clases anteriores sin llamarlas "framework". Bootstrap nada más las empaqueta juntas.

Un poco de dónde viene

Bootstrap nació en 2011 adentro de Twitter. Lo hicieron Mark Otto y Jacob Thornton porque las herramientas internas de la empresa se veían todas distintas entre sí — cada equipo usaba su propia mezcla de CSS. Lo liberaron como código abierto casi de inmediato y se volvió el framework de CSS más usado del mundo. La versión que usamos aquí (5.3) ya no depende de jQuery como las versiones viejas — usa JavaScript normal más Popper.js para acomodar los menús.

2. Cómo entra Bootstrap a la página

Un CDN es un servidor externo que ya tiene guardado el archivo de Bootstrap — en vez de bajarlo y guardarlo en tu proyecto, el navegador lo pide directo de ahí en cuanto carga la página.

<link href="https://cdn.jsdelivr.net/npm/bootstrap@5.3.8/dist/css/bootstrap.min.css" rel="stylesheet"> <script src="https://cdn.jsdelivr.net/npm/@popperjs/core@2.11.8/dist/umd/popper.min.js" defer></script> <script src="https://cdn.jsdelivr.net/npm/bootstrap@5.3.8/dist/js/bootstrap.min.js" defer></script>

Tres cosas de por qué está escrito así:

  • El orden importa. El CSS va en el <head> porque el navegador necesita saber los estilos antes de dibujar la página. Popper.js va ANTES que el JS de Bootstrap porque Bootstrap ya lo necesita cargado para saber dónde acomodar los dropdowns y tooltips — si se invierte el orden, esos componentes truenan en la consola.
  • defer le dice al navegador: bájate este script mientras yo sigo leyendo el resto del HTML, pero no lo corras hasta que ya esté todo armado. Sin esto, el script se podría ejecutar a la mitad, buscando algo que el navegador todavía ni ha leído.
  • integrity no es solo "seguridad" así en general — es como una huella digital del archivo. El navegador saca la huella de lo que de verdad se descargó y la compara con la que trae el HTML. Si no coinciden (alguien cambió el archivo en el camino), el navegador se niega a usarlo.

Esta página ya tiene los tres cargados — por eso todo lo de aquí abajo se ve y funciona de verdad, no son capturas de pantalla.

3. El grid: por qué 12 columnas

container centra el contenido con un ancho máximo; container-fluid siempre ocupa el 100% del ancho disponible. El grid divide ese ancho en 12 columnas — y no es un número que se les ocurrió nada más así: 12 se puede dividir exacto entre 2, 3, 4 y 6, así que puedes hacer mitades, tercios, cuartos y sextos sin que te sobre ni te falte espacio. Un row contiene columnas (col-N), y N dice cuántas de esas 12 ocupa cada una.

<div class="row"> <div class="col-4">...</div> <div class="col-4">...</div> <div class="col-4">...</div> </div>

Por debajo, el grid está hecho con Flexbox — un row es display: flex, y cada col-N saca su ancho a partir de esa fracción de 12 (lo pueden confirmar inspeccionando cualquier row en el navegador). El row también trae un margen negativo a los lados, que cancela el padding que traen sus columnas por dentro — así el contenido de la primera y la última columna queda pegado al borde del contenedor, en vez de quedar recorrido hacia adentro.

4. Componentes más comunes

Van en el mismo orden en que normalmente se arma una página: primero lo de arriba, al final lo de hasta abajo. En cada uno, antes del código, vale la pena entender qué problema resuelve y por qué funciona así — no solo memorizar el nombre de la clase.

Navbar

Un navbar tiene que resolver algo real: en pantalla ancha hay espacio para mostrar todos los links, pero en un celular no. En vez de escribir dos versiones del menú, Bootstrap usa un solo <ul> que vive dentro de un contenedor con la clase collapse. En pantallas chicas ese contenedor empieza oculto; un botón (navbar-toggler) con data-bs-toggle="collapse" le dice al JS de Bootstrap que, al hacer clic, le ponga o le quite la clase show a ese contenedor — eso es lo que lo hace aparecer y desaparecer. En pantallas anchas, Bootstrap simplemente ignora esa clase y hace que el menú se muestre siempre en fila.

sticky-top usa position: sticky de CSS para que el navbar se quede pegado arriba al hacer scroll, sin necesitar JavaScript. Un dropdown adentro del navbar funciona con la misma idea de mostrar/ocultar, pero además usa Popper.js para decidir de qué lado abrir el menú según el espacio que haya en pantalla.

Botones

El color de un botón (btn-primary, btn-success...) no describe un color exacto, describe qué TIPO de acción es: "primary" es la acción principal, "danger" es algo que borra o daña, "success" confirma que algo salió bien. Esto importa porque, si más adelante cambian la paleta del sitio (lo van a ver en el Bloque 6, Personalizar), un botón "danger" sigue significando lo mismo aunque su color exacto cambie.

btn-outline-{color} no es un botón distinto — es el mismo botón, pero en vez de rellenar el fondo, solo le pinta el borde y el texto de ese color, dejando el fondo transparente. El tamaño (btn-sm/btn-lg) ajusta el padding y el tamaño de letra juntos, no solo uno de los dos. El atributo disabled (ojo: es un atributo de HTML, no una clase de Bootstrap) es lo que de verdad impide el clic — que se vea gris es nada más una consecuencia de que el navegador ya sabe que ese botón está apagado.

<button class="btn btn-primary">Normal</button> <button class="btn btn-outline-primary">Outline</button> <button class="btn btn-primary btn-sm">Chico</button> <button class="btn btn-primary btn-lg">Grande</button> <button class="btn btn-primary" disabled>Deshabilitado</button>

Tipografía con utilidades

Un <h1> normalmente hace dos cosas a la vez: le dice al navegador "este es el título más importante de la página" (eso importa para SEO y para lectores de pantalla) y también "muéstralo grande". Bootstrap separa esas dos cosas: las clases display-1 a display-6 solo controlan el tamaño, sin importar qué etiqueta las lleve — las puedes poner en un <h1> y sigue siendo el título principal, o hasta en un <p> si solo quieres el tamaño grande sin que cuente como encabezado. .lead resalta un párrafo de introducción (más grande y más ligero que el texto normal), pensado para ir justo debajo de un título.

Título de bienvenida

Un texto introductorio, un poco más grande que el normal.

<div class="bg-primary text-white text-center p-4"> <h1 class="display-4 fw-bold">Título de bienvenida</h1> <p class="lead">Un texto introductorio, un poco más grande que el normal.</p> </div>

Alerts

Una alerta simple es solo CSS — un <div> con color de fondo según su clase. Lo que la hace "cerrable" son tres cosas trabajando juntas: alert-dismissible le hace espacio al botón de cerrar (le mete padding extra a la derecha); fade + show son las clases que Bootstrap usa para animar cuando algo aparece o desaparece; y el atributo data-bs-dismiss="alert" en el botón es lo que el JS de Bootstrap está escuchando — al hacer clic, le quita la clase show (dispara la animación de salida) y después borra el elemento por completo.

Una alerta simple.
Aviso: Esta se puede cerrar.
<div class="alert alert-success" role="alert">Una alerta simple.</div> <div class="alert alert-warning alert-dismissible fade show" role="alert"> <strong>Aviso:</strong> Esta se puede cerrar. <button type="button" class="btn-close" data-bs-dismiss="alert"></button> </div>

Ojo: cuando cierras una alerta, el elemento se borra del todo (no solo se esconde) — si la necesitas otra vez, hay que volver a crearla, no nomás mostrarla de nuevo.

Button groups

Un btn-group por sí solo nada más agrupa botones uno junto al otro. Lo interesante es cómo se convierte en un selector: un input type="radio" ya trae de HTML puro el comportamiento de "una sola opción entre varias con el mismo name". Bootstrap no inventa nada nuevo ahí, solo lo esconde con la clase btn-check (que le pone display: none al radio real) y usa su <label> como si fuera el botón. Al hacer clic en el label, se activa el radio escondido por la relación for/id — el mismo truco de accesibilidad que ya conocen de los formularios, nada nuevo de Bootstrap.

<div class="btn-group" role="group"> <input type="radio" class="btn-check" name="radio" id="op1" checked> <label class="btn btn-outline-primary" for="op1">Opción A</label> <input type="radio" class="btn-check" name="radio" id="op2"> <label class="btn btn-outline-primary" for="op2">Opción B</label> </div>

Badges

Un badge normal es solo una etiqueta chica con fondo — lo difícil es pegarlo en la esquina de otro elemento sin que empuje el resto del layout. Para eso se juntan tres utilidades de posición: el elemento de afuera necesita position-relative (sirve de referencia), el badge usa position-absolute con top-0 start-100 (lo manda a la esquina de arriba a la derecha), y translate-middle lo mueve medio ancho y medio alto hacia atrás — así el CENTRO del badge queda justo sobre la esquina, no su borde.

<span class="badge text-bg-primary">Nuevo</span> <button class="btn btn-primary position-relative"> Inbox <span class="position-absolute top-0 start-100 translate-middle badge rounded-pill bg-danger">3</span> </button>

Cards

Una card a propósito es un contenedor bien simple: no le importa qué le pongas adentro, solo pone un borde, una esquina redondeada y separación pareja entre sus partes (card-body, card-title, card-text). Por ser tan simple, la misma card sirve para un producto de catálogo, un perfil de usuario o una noticia — el componente no asume nada del contenido, solo del contenedor.

Un texto breve de ejemplo dentro del cuerpo de la tarjeta.

Carousel

Un error común es pensar que el carrusel "carga" la siguiente imagen cuando pasas de slide. En realidad TODAS las imágenes ya están en el HTML desde que la página cargó; lo único que cambia es cuál carousel-item tiene la clase active en ese momento — las demás están escondidas con CSS. El "salto" entre slides es una transición de CSS que dispara el JavaScript, no una carga nueva de contenido. Los botones de indicador (los puntitos) y las flechas de prev/next funcionan porque, con data-bs-target, apuntan al mismo id del carrusel — así el JS sabe a cuál controlar, aunque haya varios carruseles en la misma página.

Forms

Bootstrap solo resuelve la parte de cómo SE VE un formulario (form-control, form-label, form-check) — a propósito no toca nada de cómo funciona. Eso quiere decir que la relación id/for entre un input y su label sigue siendo cosa tuya, igual que en un formulario sin ningún framework; Bootstrap no adivina esa relación ni valida datos solo (para eso trae otras clases aparte, is-valid/is-invalid, que no vemos en esta clase).

<div class="row"> <div class="col-md-6"> <label class="form-label" for="fNombre">Nombre</label> <input type="text" id="fNombre" class="form-control"> </div> <div class="col-md-6"> <label class="form-label" for="fCorreo">Correo</label> <input type="email" id="fCorreo" class="form-control"> </div> </div>

SVG Icons

Un ícono SVG no es una imagen como las de siempre — no hay pixeles guardados en un archivo, hay puras coordenadas (el atributo d del <path>) que el navegador dibuja en el momento, dentro de un lienzo que define viewBox. Por eso el mismo ícono se ve nítido a 16px o a 200px: en cada tamaño el navegador vuelve a dibujar las líneas, no está estirando pixeles que ya existían. Y como el color se pone con el atributo fill (no con un CSS de imagen de fondo), cambiarlo es tan simple como cambiar ese valor.

<svg width="40" height="40" fill="#0d6efd" viewBox="0 0 16 16"> <path d="..." /> </svg>

5. Responsividad: por qué "mobile-first"

Las clases de columna aceptan un breakpoint: col-{breakpoint}-{N}. Lo importante no es memorizar los números, sino entender la lógica: TODAS las condiciones de Bootstrap son min-width, nunca max-width. Eso quiere decir que una clase sin breakpoint (col-12) es la base para cualquier pantalla, y cada breakpoint extra (col-md-6) solo se prende a partir de cierto ancho hacia arriba, sin tope. Por eso conviene diseñar primero para celular: el CSS que no se sobreescribe con un breakpoint más grande se queda aplicando en pantallas grandes también, así que más vale que ese CSS base sea el más simple (una columna, apilado), y no al revés.

6. Personalizar: variables que cambian sin recargar

Hasta la versión 4, la única forma de cambiar los colores de Bootstrap era con Sass: recompilabas todo el framework con tus valores nuevos ANTES de que el navegador viera una sola línea de CSS. Desde la versión 5.3, Bootstrap también deja su paleta como variables de CSS (--bs-primary, --bs-secondary...) — y esas sí las resuelve el navegador mientras la página ya está corriendo, no antes. La diferencia importa: una variable de CSS la puedes leer y cambiar con JavaScript después de que la página ya cargó (como abajo), algo que una variable de Sass ya no te deja hacer, porque para cuando el navegador la ve, ya se convirtió en CSS normal y fijo.

Cambiar --bs-primary en :root cambia el color en TODOS los componentes que la usan (botones, links, bordes) a la vez, porque esos componentes no tienen el color escrito directo — tienen escrito var(--bs-primary), y el navegador va a buscar ese valor cada vez que pinta la página.

:root { --bs-primary: #6a1b9a; --bs-primary-rgb: 106, 27, 154; }

El botón "Cambiar" de arriba hace justo eso con una línea de JavaScript, para que vean el efecto sin recargar la página — pero para la tarea, con escribir el bloque :root del código de arriba ya alcanza, no hace falta JavaScript.
